# Dataset findings

Analysis and observations behind the corpus — written for the Assignment 2
report. For how to *use* the data, see [DATASET_HANDOFF.md](DATASET_HANDOFF.md).

Every number here comes from `reports/bias_tables.md`,
`reports/raw_inspection.md` or `data/vlm_v2/manifest.json`, all generated by
the pipeline from the records it actually wrote.

## 1. The constant-label defect in the Assignment 1 VLM data

`prepare_vlm_dataset.py` wrote, for every row:

```python
"outputs": [chosen, rejected], "preferences": {"human": 1}
```

The preferred response was always in slot A and the gold label was always `1`.

**What this did not break.** The preference itself is genuine — in RLHF-V the
human-corrected response really is preferred. Position randomization does not
change that; it only moves which slot holds the preferred response and flips
the stored label with it. No instance is relabelled.

Nor could a degenerate judge exploit it. `simulate_annotators_batch`
(`open_cascade/vlm_judge.py:208`) scores **both orderings and averages**, so a
judge that always answers "A" receives `[0.5, 0.5]` and abstains. The reported
85.95% is a content-based number, not a position artefact.

**What it did break: the few-shot prompts.** `vlm_judge.py:141` renders each
demonstration's answer from its label. With `preferences` equal to
`{"human": 1}` everywhere, **every Simulated Annotator demonstration showed
`[[A]]`** — the prompt taught the judge that the answer is always A. That
pushes it toward A in both orderings, which the averaging cancels toward 0.5
confidence, and low confidence is what suppresses coverage. A plausible
contributor to the **29.51% coverage**. The new pools are balanced: 5 `[[A]]`
/ 5 `[[B]]` in `fewshot.maj.jsonl`.

Label balance before and after position randomization:

| Source | Before | After | Swap rate |
|---|---|---|---|
| rlhf_v | **5,716 A / 0 B (100.0%)** | 2,856 / 2,860 (50.0%) | 0.500 |
| mm_rlhf | **8,650 A / 0 B (100.0%)** | 4,356 / 4,294 (50.4%) | 0.496 |
| visionarena | 7,942 / 8,022 (49.7%) | 8,002 / 7,962 (50.1%) | 0.502 |
| visit_bench | 486 / 513 (48.6%) | 516 / 483 (51.7%) | 0.483 |

**Recommendation:** re-run the cascade rather than carry the old figure
forward. The prompts were degenerate and RLHF-V alone is a pilot-grade source.

Guards: `test_randomization_breaks_the_constant_label`, and `verify_export`
fails any split outside 35–65% A.

## 3. Bias analysis

### 3.1 Position bias — fixed

See §1. Randomization is seeded by `uid`, so a record's assignment does not
depend on which sources ran or in what order. Swap rates 0.48–0.50 everywhere.

VisionArena needed no correction: its raw position balance is 0.5005
(9,374 model_a vs 9,354 model_b over 29,849 battles).

### 3.2 Length bias — NOT fixed, the most serious remaining confound

P(the longer response is the preferred one):

| Source | P(longer wins) |
|---|---|
| **mm_rlhf** | **0.725** |
| **rlhf_v** | **0.700** |
| **judge_anything** | **0.692** |
| **visionarena** | **0.630** |
| visit_bench | 0.510 |

Four of five sources reward length heavily. **A judge that simply prefers the
longer response scores 63–72% without looking at the image.** Any agreement
number in that range is not evidence of visual reasoning.

Mitigations: report agreement on a length-matched subsample as an ablation,
and report per-source agreement rather than a pooled figure. `meta.len_a` and
`meta.len_b` are on every record.

### 3.3 Correction bias — why RLHF-V is a pilot

The preferred side is always the human edit, so the "model" being judged is a
human rewrite. Combined with P(longer) = 0.700, agreement on RLHF-V says
little about judge quality. It is also a different task from the paper's
model-vs-model setting. Keep it as a pilot, not a headline.

### 3.4 Ties

9,696 routed out of the main protocol and kept in `ties.jsonl` for the
confidence→0.5 test. The two VisionArena tie types are preserved separately
because "both good" and "both bad" are different kinds of indifference:

| Tie type | Count |
|---|---|
| visionarena `tie (bothbad)` | 5,193 |
| visionarena `tie` | 4,494 |
| visit_bench annotator split | 9 |

VisionArena's raw tie rate is **37.3%**, which is why the tie set is large.

### 3.5 Difficulty selection — the MM-RLHF τ knob

τ decides how easy the constructed pairs are, so it is reported rather than
tuned silently:

| τ | Prompts with a qualifying pair | Fraction | Mean min gap |
|---|---|---|---|
| 0.5 | 1,805 / 2,000 | 90.3% | 0.951 |
| **1.0** | **1,423 / 2,000** | **71.2%** | **1.439** |
| 1.5 | 659 / 2,000 | 33.0% | 2.122 |
| 2.0 | 364 / 2,000 | 18.2% | 2.458 |
| 3.0 | 51 / 2,000 | 2.6% | 3.539 |

τ=1.0 is the default. **One pair per prompt**, chosen at random among
qualifying pairs — not the widest gap, which would systematically select the
easiest comparison in every group, and not all pairs, which would put
correlated instances in one split.

### 3.6 Language and category skew

VisionArena spans 90 languages. English 9,608 (~60%), then Russian 1,764,
Chinese 1,239, Vietnamese 818. Categories: ocr 2,244, captioning 1,442,
diagram+ocr 1,373, homework+ocr 1,333. Both on `meta.lang` / `meta.category`.
An English-only main set with other languages as a reported slice is the
natural protocol.

### 3.7 Reference skew

288 pairs involve the VisIT-Bench human-verified reference, flagged with
`meta.has_reference`. The strongest model beats the reference only ~27% of the
time, so this slice should be reported separately.

### 3.8 Leakage

Splits are drawn over **connected components of (group id, perceptual hash)**,
so neither a prompt group nor an image can cross a boundary — necessary
because one image appears under several instructions and sources overlap.
26,207 components over 31,635 records; the largest holds 59 (0.2%), so no
perceptual-hash collision chained unrelated images. `assert_no_leakage`
enforces it on every run.

## 4. Bottlenecks encountered

1. **Published size is dominated by media for modalities you aren't using.**
   MM-RLHF's dataset card suggests ~35 MB of metadata; a usable download is
   **30 GB**, because the image archives ship in the same repo. JudgeAnything
   looks like "3,000 pairs" and is **10,325 files**, 70% of them `.mp4`/`.wav`.
   Neither the card nor the datasets-server row count reveals this. Addressed
   with per-source `allow_patterns` / `ignore_patterns`.

2. **Gated access.** VisionArena-Battle requires accepting terms while signed
   in, plus `hf auth login`. Browser device login suffices; no read token needed.

3. **Interrupted transfers do not always resume.** MM-RLHF's 15 GB `long.zip`
   stalled; re-running with `--force` started a *new* partial and abandoned
   11.6 GB already on disk. Plain re-running resumes. Download wall time:
   VisionArena 10,698 s, MM-RLHF 10,972 s.

4. **Annotator supply constrains Simulated Annotators (Ind.).** Only
   VisionArena carries annotator ids, and its votes are heavy-tailed: 13,655
   unique voters over 29,849 battles, mean 2.19 each, 5,766 of them voting once.

   | Requirement | Corpus-wide | Within fewshot split |
   |---|---|---|
   | K=1 (≥2 labels) | 2,730 | 723 |
   | **K=2 (≥3 labels)** | **1,339** | **477** |
   | K=3 (≥4 labels) | 767 | 267 |
   | K=5 (≥6 labels) | 365 | 116 |

   This works only because the split deliberately concentrates prolific
   annotators into `fewshot` (§5.2).

5. **Context length caps K.** Each few-shot example embeds one image
   (~1,280 tokens), restricting K to {1, 2}. No pair exceeds the budget at
   K=2, but the ceiling is why the K grid is small — and why video is out of
   scope (§6).

6. **A released artefact did not match its description** — JudgeAnything, §7.

## 5. Design decisions worth defending

### 5.1 Dedup keys on the comparison, not on the prompt

A record is a duplicate only if its **image, prompt and unordered response
pair** all match another's. Deduplicating on image + prompt alone is wrong
here, and we got it wrong twice before settling:

- **Within a source**, a prompt-level key removed **22% of the corpus**.
  VisIT-Bench compares seven models on one image and prompt; six of every
  seven comparisons were being discarded as "duplicates".
- **Across sources**, the same key then removed **76 JudgeAnything records**
  (25% of that source), because 19 of its queries use an image and
  instruction that also appear in VisIT-Bench. Those were still distinct
  comparisons — different models, different responses.

The leakage such a rule would guard against is already covered: the
group-aware split merges components on perceptual hash, so every record
sharing an image lands on one side of the calibration/test boundary whatever
its source (§3.8).

With the correct key, genuine duplicates are only **134 records (0.3%)** —
126 from MM-RLHF, 7 VisionArena, 1 VisIT-Bench.

### 5.2 The fewshot split over-samples prolific annotators, but only to 50%

Both halves matter:

- **Without over-sampling**, an annotator with 10 votes corpus-wide expects ~1
  inside a 10% split, so nobody clears K+1 there and the Ind. pools come out
  empty — even though 1,339 annotators qualify corpus-wide.
- **Without the 0.5 cap**, fewshot fills entirely from the only source with
  annotator ids. An uncapped run gave a fewshot split of **2 / 0 / 3,130 / 2**
  across the sources with annotator ids, so the Maj. pools would have shown one
  dataset's style to a judge that has to grade four. Capped, it is
  **313 / 63 / 2,277 / 480**.

Fewshot is prompt material and is never evaluated on, so concentrating
annotators there costs nothing in validity.

### 5.3 Maj. pools are stratified across sources

Round-robin rather than uniform, for the same reason: the corpus is dominated
by VisionArena, and each pool should look like the corpus rather than its
largest member.

### 5.4 Adapters do one job

Adapters only convert a source to canonical records — no randomizing, dedup or
splitting. Those are shared stages, so every source gets identical treatment
and the funnel compares like with like.

## 6. Scope: image + text only

Video is not merely expensive, it **breaks the method**. K is already capped at
1–2 by one image per few-shot example; a video at 8 frames (~10K tokens) forces
K=0. With K=0 every simulated annotator receives an identical prompt, so they
agree trivially — the confidence measure collapses, and with it the threshold
and the guarantee. Simulated Annotators *is* the contribution. The payoff would
be small anyway (~3–4K instances).

The pipeline treats this as configuration, not architecture: `Record.modality`
is `image|video|audio`, `run.py --modalities` gates the extension sets, and
`config.py` documents the exact download patterns to add.

**Safety content excluded** (MM-RLHF `safety/`, 984 rows): a different judging
task whose refusal behaviour would confound general preference agreement.

## 7. JudgeAnything: what is usable, and an A1 correction

### Why only 100 of its 1,500 queries are usable

JudgeAnything is an **any-to-any** benchmark: 1,500 queries over 15 task
types, 100 each. Most are for modality combinations this method cannot judge
at all.

| Block | Queries | Status |
|---|---|---|
| Generation tasks (X → image/video/audio), 10 types | 1,000 | **impossible** — the things compared are generated media; a text judge has nothing to compare |
| Video2Text, Audio2Text, AudioVideo2Text | 300 | out of scope — video/audio input (§6) |
| Text2Text | 100 | judgeable but text-only; could feed the *text* cascade |
| **Image2Text** | **100** | **our modality** |

Of the 100 Image2Text queries, 77 are single-image and 23 carry 2–5 images,
which the judge prompt cannot take. 77 queries × 4 battles = 308, of which
307 have responses on both sides.

So the small yield is not filtering loss — the benchmark is broad across
modalities rather than deep within image→text.

### The join, and the two traps in it

```
X2XRawBenchmark/TaskAnything.json          1,500 queries: uniq_id, task_name,
                                           question, image_path
Arena/arenaresult/.../gang_Understanding_record.json
                                           500 ids -> 4 battle strings each,
                                           "<model_a> vs <model_b> <winner> wins"
Arena/<model>/<Model>.json                 that model's answer, same uniq_id
```

Ids match 500/500. Two things cost a full investigation cycle:

1. **`ResponseCollection/JudgeAnything.json` is the wrong response file.** It
   holds answers from Phi3V, claude, gpt-4o and qwen-vl-max — models that
   never appear in the battle records. The battles are between eight *Arena*
   models, whose answers are in the per-model files. Joining to the wrong one
   returns nothing and looks like mismatched ids.
2. **Model names cannot be split on whitespace.** `Baichuan-Omni-1.5` and
   `Next-GPT` contain hyphens and dots, and the trailing winner token is not
   delimited, so names are matched against the known model set.

Also: `answer` is a dict on some models and a list of dicts on others, with
`type` spelled both `"text"` and `"Text"`.

### What it contributes

307 pairs, 1 tie, label split 167 A / 139 B before randomization — already
balanced, unlike RLHF-V. All eight Arena models appear, and each record
carries the task's evaluation `checklist` in `meta` (kept out of the judge
prompt).

Its value is distributional rather than volumetric: these are any-to-any
models (CoDi, Next-GPT, ModaVerse) whose outputs are much weaker than the
arena VLMs in VisionArena, so the pairs sit at a different point of the
quality range.

### The A1 correction still stands

The Assignment 1 report describes JudgeAnything as *"annotated by 12
annotators with cross-validation, giving 15 annotations per item and 45,000
human judgments."* **The published artefact carries aggregated battle
outcomes with no annotator ids**, so this source cannot feed Simulated
Annotators (Ind.) or the inter-annotator agreement analysis.

**Action: correct the dataset table in the report.**

## 8. Reproducibility

- Seed 42 throughout. Two consecutive full runs produced identical counts at
  every stage (41,545 → 41,465 → 41,331 → 31,635).
- Caps are seeded random subsets, never prefixes. Every source is stored in a
  correlated order, so a prefix bakes in selection bias — the raw inspection
  originally reported *zero* MM-RLHF video rows for exactly this reason.
- 51 tests in `tests/test_prepare_data.py`, no network or GPU.
- `verify_export` re-reads the written splits through the repo's own loaders.
- Every stage that drops or reclassifies a row records it in the funnel while
  it happens, so the tables above are logged rather than reconstructed.
